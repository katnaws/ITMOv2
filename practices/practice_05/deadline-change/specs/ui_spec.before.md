# Study Space — UI‑спека (до согласования)

Фича: перенос дедлайна задания (изменение поля deadline)
Объём: аккуратное расширение текущего React‑дашборда из практики 4. Перерисовок и перестройки проекта нет.

Контекст
- Текущий UI: React + Vite, Python HTTP‑бэкенд мостом в MCP `study_tracker`.
- Доступные инструменты MCP: add_task, list_tasks, update_task_status, study_dashboard. Инструмента для изменения дедлайна пока нет — см. контракт ниже.
- Визуальные паттерны: переиспользуем Modal, кнопки, icon-button, формы из `dashboard/src/main.jsx` и `style.css`.
- Даты: только дата (YYYY-MM-DD), часовой пояс Europe/Moscow. Просроченные даты разрешены; «сегодня» не просрочено; задачи со статусом done не считаются просроченными в отображении.
- Персистентность: в real — общая с MCP SQLite; в demo — временная БД. Реальные задания в демо не создаём.

Не цели
- Не меняем статус/название/курс — редактируем только deadline.
- Не меняем runner/skill/MCP внутри этой спеки. Этот документ не вносит код.
- Не добавляем новые страницы/навигацию.

Точка входа в UI
- В каждой строке задания добавить действие «Перенести срок»:
  - Размещение: в колонке дедлайна рядом с датой.
  - Элемент: небольшая icon-button с подсказкой «Перенести срок». Переиспользуем `.icon-button`; иконка CalendarDays.
  - Доступность: `aria-label="Перенести срок: <название задания>"`.
  - Взаимодействие: мышь и клавиатура (Tab + Enter/Space).

Модальное окно «Перенос дедлайна»
- Используем существующий `<Modal>` и стили `.modal`.
- Заголовок: «Перенос дедлайна», кнопка закрытия `aria-label="Закрыть"`.
- Описание: «Смените срок для задания. Даты по московскому времени.» В демо добавить: «Изменения сохраняются в демо‑БД до перезапуска.»
- Содержимое:
  - Блок-сводка (read‑only): название задания и текущий дедлайн (формат как в таблице, ru-RU).
  - Форма из одного поля:
    - Метка: «Новый дедлайн».
    - Поле: `<input type="date" name="deadline" required>`, предзаполнить текущим дедлайном.
    - Подсказка (тихая): «Формат ГГГГ‑ММ‑ДД. Сегодня не считается просроченным. Разрешены прошедшие даты.»
  - Область ошибок: `.form-error` для валидации/ошибок сервера.
  - Кнопки: «Отмена» (secondary) и «Сохранить» (primary).

Состояния кнопки и валидация
- «Сохранить» неактивна, если:
  - Идёт отправка (saving=true).
  - Дата пустая или невалидна для `<input type=date>`.
  - Дата совпадает с текущим дедлайном (NOP). Показать подсказку «Дата не изменилась» и держать «Сохранить» выключенной.
- «Отмена» закрывает модалку, кроме момента активной отправки.
- При отправке:
  - Показать LoaderCircle в кнопке.
  - Блокировать повторные отправки.

Доступность
- Фокус при открытии — на поле даты (autoFocus). Модалка перехватывает фокус; ESC закрывает, если не сохраняем.
- Все элементы достижимы с клавиатуры, имеют понятные метки.
- Ошибки inline имеют `role=alert`.
- Сохраняем визуальные состояния фокуса из текущего CSS.

Взаимодействия и отклики
- Успех: закрыть модалку, показать тост «Дедлайн перенесён», тихо обновить данные.
- Ошибка: модалка остаётся открытой, текст ошибки в `.form-error`, поля не очищать.
- История: новый MCP‑вызов виден в «Истории MCP‑вызовов» с названием инструмента и аргументами.

Согласованность с дизайном
- Используем текущие цвета/типографику/отступы; без новых глобальных стилей.
- Иконки — из lucide-react; для действия — CalendarDays.
- Таблицу не перестраиваем, колонок не добавляем.

Что должно обновиться после успеха
- Перерисовать:
  - Строку задания: новая дата и метка просрочки (`.task-date.late`).
  - Сортировка: список задач отображает порядок, полученный от backend; после обновления состояния порядок может измениться согласно новой дате.
  - Карточки сводки: число просроченных; проценты прогресса меняются только за счёт пересчёта overdue; по статусам — без изменений.
  - Правая колонка:
    - «На горизонте» — новые ближайшие.
    - «В своём темпе» — next_task может измениться (на стороне логики).
- Персистентность:
  - Real: изменения переживают рестарт.
  - Demo: живут до рестарта backend; обновления страницы/модалки переживают.

Режимы и автообновление
- Уважаем переключатель mode (real|demo). В модалке — соответствующее описание.
- Если режим сменился во время открытой модалки:
  - Выключить «Сохранить» и показать «Режим данных изменён. Закройте окно и повторите действие.»
  - Закрыть — всегда можно; повторное открытие — в текущем режиме.
- Периодическое обновление (30с) оставить. Защита от устаревших данных — через текущий ticket `generation` в App.

Клиентская валидация
- Обязательная дата; базовая проверка за счёт `<input type=date>`.
- Прошедшие даты разрешены. «Сегодня» не просрочено.
- Не вводим часовой пояс в UI; трактуем как date‑only в Europe/Moscow и в UI, и на backend.
- Не меняем другие поля.

Обработка ошибок (сервера/моста)
- Несуществующий ID: «Задание не найдено. Обновите список.»; модалка остаётся.
- Пустая/неверная дата: клиент не отправляет; если сервер вернул 400 — показать «Неверная дата».
- Проблемы demo/real БД: показывать текст сообщения сервера; спец. логики в UI нет, кроме пометки демо.
- Ошибки сети/моста MCP: страничный баннер (существующий) + inline ошибка в модалке; разрешить повтор.

Состояния гонок
- Обновление vs отправка: отправляем с актуальным task.id и выбранной датой; после успеха — `refresh` перезагружает состояние и перезаписывает локальные данные (last write wins).
- Гонка режимов: см. раздел «Режимы и автообновление».
- Запрет параллельных вызовов — «Сохранить» выключена во время отправки.

Доступность кнопки в строке
- Элемент — button, фокусируемый, с видимым фокусом и `aria-label`, включающим `task.title`.
- Минимальная зона активации ≥ 32×32 CSS px; используем отступы `.icon-button`.
- По желанию: `title="Перенести срок"` для мыши.

MCP/HTTP мост — предлагаемый контракт
- Новый MCP‑инструмент: `update_task_deadline`.
  - Аргументы: `{ task_id: number, deadline: string /* YYYY-MM-DD */ }`.
  - Поведение: изменить только дедлайн; сохранить title, course, status. Валидация: запрет пустой/невалидной даты; разрешить прошлые; трактовать Europe/Moscow; «сегодня» не просрочено; статус `done` не помечать как просроченный в метриках.
  - Ошибки:
    - `task_id` отсутствует → "Task not found".
    - Неверный `deadline` → "Invalid date".
    - Пустой `deadline` → "Deadline is required".
- HTTP‑эндпойнт (по аналогии с существующим мостом):
  - `POST /api/tools/update_task_deadline?mode=real|demo`.
  - Тело: JSON, как выше.
  - Успех: 200 `{ ok: true }` (опционально вернуть `{ task: {...} }`).
  - Ошибка: 400 `{ error: string, result: { isError: true, content: [{ type: 'text', text: string }] } }`.
  - Перезагрузка состояния: без изменений; UI после успеха вызывает `GET /api/state?mode=...`.

Отображение в истории

Примеры сценариев
- Пользователь переносит на +5 дней → тост «Дедлайн перенесён», список и «На горизонте» обновляются.
- Пользователь выбирает ту же дату → «Сохранить» неактивна, подсказка «Дата не изменилась».
- Некорректная дата → браузер не даёт отправить; после попытки — inline‑ошибка.
- Сервер 400 (не найден ID) → inline‑ошибка «Задание не найдено. Обновите список.», модалка остаётся.
