## Что сделано

Доработан **Study Space из практики 4**: можно перенести дедлайн уже созданного задания. Раньше были добавление, просмотр, смена статуса и сводка. Теперь есть инструмент MCP `update_task_deadline` и модалка в интерфейсе.

**Логика — OpenSpec 1.14.1, UI — GitHub Spec Kit 1.2.5.** Это одна фича с двумя согласованными частями. Фреймворки задают процесс разработки; они не являются библиотеками, встроенными в приложение.

После первой попытки с преимущественно ручными шаблонами сделан новый прогон на исходном коде без переноса дедлайна. GPT‑5 через два чата OpenCode подготовил спецификации и планы. Когда VseLLM вернул `402 provider.quota`, пользователь разрешил Codex завершить работу самостоятельно. Код, тесты и завершение процессов нового прогона выполнены Codex. Не говорите, что весь итоговый код написал GPT‑5.

## Речь на 60–90 секунд

> Я расширила учебный трекер Study Space переносом дедлайна. Для логики использовала процесс OpenSpec: описание изменения, дельту требований, дизайн и задачи, затем реализацию, проверку и архив с обновлением основной спецификации. Для интерфейса использовала Spec Kit: конституцию, спецификацию, уточнения, план, задачи и сверку реализации. Две стороны согласовали общий API до нового прогона кода. Интерфейс вызывает Python HTTP-мост, тот обращается к MCP-серверу, а MCP работает с SQLite. Меняется только срок; статус и остальные поля сохраняются. Проверены успешное сохранение, сохранение после перезагрузки, сегодняшняя и прошлая даты, ошибки и повтор. Модель использовалась при разработке; для работы самого интерфейса она не нужна. Из-за лимитов VseLLM реализацию после подготовки GPT‑5 завершил Codex с моего разрешения. Сравнение описывает опыт двух процессов на разных частях одной фичи.

## Как устроено приложение

```text
React UI → HTTP POST → Python bridge → MCP stdio → SQLite
          ← обновлённая задача и сводка ←
```

- UI: [main.jsx](../practice_04/dashboard/src/main.jsx), React/Vite. Показывает модалку, проверяет ввод для удобства, отправляет запрос, обновляет состояние.
- Мост: [dashboard/server.py](../practice_04/dashboard/server.py). Проверяет HTTP-запрос и разрешённый инструмент, вызывает MCP. Сам SQL не выполняет.
- Бизнес-логика: [MCP server.py](../practice_04/mcp/study_tracker/server.py). Проверяет аргументы, сохраняет срок параметризованным SQL и вычисляет представление задачи.
- SQLite хранит задания. Дедлайн — календарная дата без времени. Сегодня определяется по `Europe/Moscow`.

LLM не встроена в UI. Возможность попросить модель вызвать MCP — отдельный способ пользоваться теми же инструментами.

## Что согласовали до новой реализации

[Logic negotiation](frameworks/negotiation.logic.md) и [UI negotiation](frameworks/negotiation.ui.md) фиксируют исходные предложения и окончательное решение. Независимый UI before не задавал точный транспорт; затем стороны договорились о существующем MCP envelope, endpoint и ошибках.

Общий [контракт](frameworks/contract.yaml) — описательный YAML, а не полная OpenAPI-схема:

```http
POST /api/tools/update_task_deadline?mode=demo
Content-Type: application/json

{"task_id": 3, "deadline": "2026-11-15"}
```

Успех HTTP 200:

```json
{"content":[{"type":"text","text":"<JSON-строка обновлённой задачи>"}],"isError":false}
```

Здесь `text` содержит строку JSON задачи, а не объект. Пример ID и даты выше учебный; сначала надо узнать настоящий ID через список заданий.

| Ситуация | Поведение |
| --- | --- |
| Успех | 200, MCP `isError: false` |
| Неверные аргументы или неизвестный ID | 400, MCP `isError: true`; некорректное HTTP-тело может вернуть `{error}` от моста |
| Недопустимые Host/Origin | 403 |
| Мост работает, но не смог выполнить MCP | 502 |
| Сам HTTP-сервер выключен | Сетевая ошибка, HTTP-ответа 502 нет |

`task_id` — положительный целый, bool не подходит. Дата — настоящая календарная `YYYY-MM-DD`. Отсутствующие/лишние аргументы отклоняются.

## Правила, которые полезно запомнить

- Меняется только `deadline`; `id`, `title`, `course`, `status`, `created_at` остаются прежними.
- `days_left` и `overdue` пересчитываются. Сегодня: `days_left=0`, `overdue=false`.
- Прошлая дата разрешена. Активная задача с ней просрочена; `done` не просрочена.
- Та же дата в API — успешная операция без изменения данных. В UI «Сохранить» выключена.
- При сохранении блокируются повторная отправка, ввод и закрытие. Пока модалка открыта, нельзя переключить real/demo.
- При ошибке модалка остаётся открытой, введённая дата сохраняется, доступен повтор, сообщение по-русски.
- После успеха модалка закрывается, UI перечитывает состояние и показывает уведомление. Если запись прошла, но перечитывание не удалось, UI просит обновить список.

## Показ за 5–7 минут

Подробный запуск: [DEMO](DEMO.md). Сейчас: http://127.0.0.1:8765/?mode=demo.

1. За минуту покажите две спецификации и контракт. Назовите распределение фреймворков.
2. В demo найдите задачу и нажмите карандаш рядом с датой.
3. Покажите текущую дату и фокус в поле. Та же дата и пустое поле блокируют сохранение. Отмена не меняет задание.
4. Выберите будущую дату и сохраните. Покажите уведомление и новый срок. Обновите страницу и проверьте его снова.
5. В истории MCP-вызовов найдите `update_task_deadline` с ID и датой.
6. Перенесите активную задачу на сегодня, затем в прошлое. Покажите разницу просрочки. У выполненной задачи статус сохранится.
7. Откройте отчёты: настоящие 400/403 и отдельный браузерный сценарий 502 с успешным повтором. Скажите прямо: 502 там имитируется, это тест обработки сбоя.

Если список меняет порядок после переноса, находите задачу по названию/ID. Проверки тоже не зависят от номера строки. Скриншоты и временные пути не заменяют живое демо и сохранённые JSON-отчёты.

## Запуск и проверки из корня репозитория

Для отдельной репетиции с временными базами:

```sh
npm --prefix practices/practice_04/dashboard run build
python3 practices/practice_05/frameworks/tests/demo_server.py --port 8765 --meta /tmp/practice05-demo.json
```

Если сервер уже работает, второй не запускайте. При занятом порте можно выбрать `--port 0`; фактический URL появится в JSON. Свой процесс останавливается Ctrl+C. Оба режима этого помощника используют временные базы и теряют данные при завершении процесса.

```sh
bash practices/practice_04/runner.sh
python3 practices/practice_04/dashboard/check.py
python3 practices/practice_05/frameworks/tests/deadline_check.py
```

Runner прошёл MCP/bridge и сборку React. Полный HTTP check выполнен дополнительно, потому что runner использует bridge-only. Расширенный тест делает 31 вызов в 6 группах: инварианты, типы, календарь, повторы, перезапуск MCP, HTTP и изоляция режимов. Browser-тест подтвердил 4 группы поведения без ошибок JavaScript.

Python-скрипты выводят JSON в stdout. Для нового сохранённого файла используйте, например, `python3 practices/practice_04/dashboard/check.py > /tmp/practice05-http-check.json`.

## Можно ли просить модель добавлять дедлайны через MCP?

**Да.** Если в OpenCode или другом клиенте подключён `study_tracker` и модель поддерживает вызов инструментов, можно попросить её добавить задание или изменить срок. Она должна выбрать инструмент и аргументы; сервер проверит их и выполнит операцию.

| Инструмент | Для чего |
| --- | --- |
| `add_task(title, course, deadline)` | Создать задание |
| `list_tasks(course?, status?)` | Узнать задания и их ID |
| `update_task_status(task_id, status)` | Изменить статус: todo / in_progress / done |
| `update_task_deadline(task_id, deadline)` | Изменить срок существующего задания |
| `study_dashboard(as_of?)` | Получить сводку |

Примеры запросов, которые можно адаптировать под свои данные:

- «Покажи мои задания по курсу Математика».
- «Добавь задание “Подготовить доклад”, курс “История”, срок 15 ноября 2026 года».
- «Найди мой доклад по истории и перенеси его дедлайн на 18 ноября 2026 года».

При одинаковых названиях или неоднозначной дате модель должна уточнить выбор. Для переноса сначала нужен настоящий ID из `list_tasks`. Новый инструмент может потребовать переподключения MCP/обновления каталога. Если лимит модели исчерпан, эта возможность временно недоступна, но UI и сервер работают без LLM.

### Как сделать данные модели видимыми в UI

Нужен **один и тот же файл SQLite**. Просто использовать любую временную базу с обеих сторон недостаточно.

| Запуск | SQLite |
| --- | --- |
| Обычный MCP по умолчанию | `practices/practice_04/mcp/study_tracker/data/tasks.sqlite3` |
| Обычный UI real без переопределения | Тот же файл по умолчанию |
| Текущий сервер-помощник real/demo | Две отдельные временные базы; реальные пути в `/tmp/practice05-framework-runtime/current.json` |
| Обычный UI demo | Отдельная временная база процесса |

Для общей демонстрации настройте MCP-клиенту `STUDY_TRACKER_DB` с точным путём `real_db` текущего помощника и откройте UI в real. В этом специальном запуске real тоже тестовый. После перезапуска помощника путь изменится; не используйте старый. Любая другая temp-база клиента сама по себе не появляется в UI demo. Конфигурация подключения здесь автоматически не менялась.

## Где история, а где итог

Актуальные материалы — `frameworks/`. Папка `deadline-change/` и верхняя `.specify/` сохранены как первая попытка. Исходный отдельный ревьюер не входит в текущий проект. Не ссылайтесь на его тесты и спецификации при защите переноса дедлайна.

[Журнал OpenCode](frameworks/evidence/opencode-commands.json) — список фактически выполненных агентом команд, с ID сессий, временем, результатом и ошибками. Это доказательство процесса, а не часть приложения. Неудачные команды там тоже сохранены.

Сырые пути `/tmp/...` в журналах относятся к временному прогону. Текущая папка с артефактами дополнительно проверена после переноса. Проект локальный учебный; production-аутентификация и сравнительный замер быстродействия не реализованы. Все обещания в спецификациях привязаны к наблюдаемому поведению, а не к непроверенным процентам надёжности.

Перед защитой откройте демо, две спеки, контракт, сравнение и отчёты. Проверьте, что сервер отвечает и вы показываете тестовые данные. Коммиты и push для подготовки не нужны.
