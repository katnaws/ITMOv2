UI спецификация (draft v2) — «Ревьюер diff с маскированием секретов»

Цель
- Предоставить понятный интерфейс для проверки и ревью diff: сначала локально замаскировать секреты и показать предпросмотр очищенного diff, затем по отдельной кнопке отправить очищенный diff на реальное ревью модели (VseLLM).

Главные принципы UX и безопасности
- Исходный diff вводится пользователем в textarea и виден только там; исходный сырой текст не отображается в других блоках, не логируется и не сохраняется локально.
- Секреты не показываются как отдельный список; пользователю доступен сравнимый просмотр исходного (в textarea) и очищенного diff (предпросмотр), с подсчетом количества замен.
- Редактирование исходного diff полностью сбрасывает предпросмотр и отключает возможность отправки «старого» результата на ревью.
- Внешний сервис получает только очищенный diff; исходный diff никогда не отправляется наружу.
- Доступный русский интерфейс: понятные подписи, aria‑атрибуты, видимый фокус.

Экраны/секции
1) Ввод и предварительная проверка
   - Поле «Вставьте unified diff» (textarea) с подсказкой.
   - Счетчик Unicode код‑поинтов и лимит 20000; >20000 — немедленное сообщение об ошибке, disable кнопки.
   - Мягкое предупреждение «Текст не похож на unified diff. Его всё равно можно отправить.» при отсутствии признаков diff.
   - Кнопки:
     - «Проверить и скрыть секреты» — запускает локальную редакцию (без запроса к сервису), формирует очищенный diff и количество замен.
     - «Очистить» — сбрасывает все состояния (с подтверждением), не сохраняет данные.

2) Предпросмотр очищенного diff
   - Показ: «Очищенный diff», безопасный текст.
   - «Количество замен: N».
   - Кнопки:
     - «Отправить очищенный на ревью» — отправляет только очищенный diff на реальное ревью (VseLLM).
     - «Изменить исходный diff» — фокус в textarea; при любом изменении предпросмотр скрывается, кнопка отправки очищенного становится недоступной.
   - Индикаторы состояний: Idle → PreviewReady → Sending → Success/Error.

3) Результат ревью
   - Summary: краткая сводка.
   - Risks: до 3 пунктов (file?/line?/evidence?/risk) — безопасный текст, без HTML.
   - Checks: массив строк.
   - Ошибки: понятные сообщения для 422/413/502 и сетевых/таймаутов.

Поведение и валидации
- Обязательность: diff не пустой.
- Лимит: ≤20000 Unicode код‑поинтов; >20000 — немедленное сообщение и запрет действий.
- Формат: мягкая эвристика для unified diff (diff --git, +++/---, @@).
- Сброс предпросмотра: любое изменение исходного diff скрывает блок предпросмотра и отключает отправку очищенного.
- Безопасный рендер: только textContent; не вставлять innerHTML из данных.
- Не сохранять данные в LocalStorage/Session/IDB; не логировать сырой diff/секреты/ключи.

Минимальный API для согласования (предложение)
- POST /api/redaction/preview — локальная редакция может выполняться на клиенте, но для согласованности можно предложить серверный превью (опционально). Если на сервере не требуется, UI делает это локально и этот endpoint исключается.
- POST /api/reviews — отправка очищенного diff на ревью (VseLLM).
  - Request: { "redacted_diff": string } // ровно очищенный diff, не исходный.
  - Success: { "summary": string, "risks": Array<{ file?: string, line?: number, evidence?: string, risk: string }>, "checks": Array<string> } // ≤3 risks
  - Errors: { "error": { "code": "UNPROCESSABLE_CONTENT"|"CONTENT_TOO_LARGE"|"LLM_UPSTREAM_ERROR", "message": string } }
  - Примечание: сервер не возвращает исходный diff; может вернуть только агрегированные сведения.

Состояния и доступность
- Элементы имеют связанные label/aria‑describedby; статусные области имеют aria‑live.
- Фокус управляем: из textarea в предпросмотр, обратно на редактирование.

Наблюдаемость/индикаторы
- Явная индикация во время «Проверить и скрыть секреты» и «Отправить очищенный на ревью».
- Показ ошибок без деталей сервера, локализуемые строки на русском.

Ограничения/не делаем
- Не показывать отдельный список секретов.
- Не отправлять исходный diff внешним сервисам.
- Не хранить сырой diff локально.

Открытые вопросы для согласования с логическим чатом
- Нужен ли серверный endpoint для превью (или UI выполняет редактирование полностью на клиенте)?
- Требуются ли дополнительные поля в успешном ответе (например, score/traceId)?
- Нужны ли метки уровня рисков/проверок (severity/status), или достаточно простых строк?
