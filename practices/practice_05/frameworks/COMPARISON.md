# OpenSpec и Spec Kit: опыт на одной фиче

Фича — перенос дедлайна в Study Space. **OpenSpec 1.14.1 использован для MCP/HTTP-логики, GitHub Spec Kit 1.2.5 — для React UI.** Это сравнение процессов на двух согласованных частях одного продукта, а не эксперимент с двумя одинаковыми реализациями. Объём работы различается; время и качество кода как сравнительные метрики не измерялись.

| Вопрос | OpenSpec: логика | Spec Kit: UI |
| --- | --- | --- |
| Отправная точка | Существующая спецификация MCP/bridge и изменение к ней | Конституция проекта, пользовательский сценарий новой модалки |
| Формулировка | proposal → дельта requirements/scenarios | specify → spec и clarify |
| Проектирование | design: MCP-инструмент, whitelist моста, инварианты | plan: существующие компоненты, состояние модалки, дата, ошибки |
| План работы | tasks: 5 пунктов | tasks: T001–T009, 9 пунктов |
| Подготовка агента | `instructions ...` и status сообщают зависимости артефактов | Сгенерированные `.opencode/commands/speckit.*.md` описывают стадии; скрипты создают структуру и проверяют prerequisites |
| До кода | proposal/specs/design/tasks готовы; применён agreed contract | Отдельный UI before, согласованный spec, plan, tasks, анализ GPT‑5 без critical/high findings |
| Реализация | Codex следовал apply и реализовал логику/проверки | Codex следовал implement, проверил чек-лист и выполнил UI-задачи |
| Завершение | CLI validate, archive; дельта синхронизирована в основную spec | Сверка по инструкции converge: 9 требований/9 задач, findings отсутствуют; итог записан Codex |
| Что проверяет инструмент | Структуру и согласованность формата спецификаций; не поведение программы | Prerequisite-скрипт — наличие документов; анализ/converge требуют рассуждения агента |
| Подтверждение кода | Настоящие MCP/HTTP тесты, временная SQLite, перезапуск MCP | Chrome/Playwright: UI → HTTP → MCP → SQLite, перезагрузка, границы и повтор после ошибки |

## Что изменило согласование

Независимый UI before описывал желаемый пользовательский поток без имени endpoint и формата envelope. Логика опиралась на существующий MCP и правила bridge. Согласованный [контракт](contract.yaml) зафиксировал:

- `POST /api/tools/update_task_deadline?mode=real|demo`, `{task_id, deadline}`.
- Настоящий MCP envelope на успехе; HTTP 400/403/502 разделены по причинам.
- Только deadline меняется; derived-поля пересчитываются по Москве.
- Прошлое разрешено, сегодня не просрочено, done не просрочено.
- API принимает ту же дату как no-op; UI блокирует неизменённую дату.
- UI локализует ошибки, сохраняет введённую дату для повтора, блокирует режим при открытой модалке.

Первоначальные предложения в negotiation сохранены как ход обсуждения; финальные решения записаны в их конце и в after-спеках. Before не переписывались под готовый код.

## Что оказалось полезным

OpenSpec удобен для небольшой доработки существующего поведения: рядом видны исходные правила, добавленные сценарии и завершённый архив. Реальный `archive` обновил основную спецификацию, а не просто переместил Markdown в другую папку.

Spec Kit помог разложить UI на наблюдаемые требования, план и последовательность задач. Анализ до реализации выявил пробелы в проверках и quickstart; перед кодом добавлены инструкции запуска и отдельная задача проверки браузером. Сняты необоснованные численные цели времени/надёжности. Сверка converge привязана к реальным результатам тестов.

В обоих случаях CLI не написал и не проверил приложение самостоятельно. Тексты и код выполняли агенты; структура процесса делала решения и невыполненную работу видимыми.

## Ограничения и трудности

При подготовке OpenSpec агент сначала вручную создал каталог, поэтому `new change` вернул «already exists». Это сохранено как ошибка; последующие инструкции, validate, apply и archive выполнены на этом изменении. Успех этой первой команды не заявляется.

В OpenCode установленный `run` не поддерживает `--command`; стадии Spec Kit выполнялись по сгенерированным инструкциям и официальным shell-скриптам. Нет заявления о запуске `specify workflow run speckit` или автоматического полного pipeline. При работе без Git feature выбрана явно, без создания ветки/коммита. После переноса папки её prerequisites повторно проверены с `SPECIFY_INIT_DIR`.

VseLLM исчерпал квоту на стадии перехода к реализации. GPT‑5 подготовил процесс в двух чатах; Codex завершил код и проверки после разрешения пользователя. Поэтому сравнение не измеряет исключительно работу GPT‑5.

Первая попытка с ручными шаблонами сохранена отдельно в `../deadline-change/`; она не используется как доказательство полного нового процесса. Подробные команды и первичные отчёты: [WORKFLOW](WORKFLOW.md), [evidence](evidence/).

Справочные первичные источники: [OpenSpec](https://github.com/Fission-AI/OpenSpec), [GitHub Spec Kit](https://github.com/github/spec-kit). Здесь выводы опираются на установленные версии и сохранённые локальные артефакты, а не на предположение о работе CLI.
